testing the second half of the [boot-path audit](C9-BOOT-AUDIT-2026-10-12.md):

## Interpretation

**Identical failure to the original L1** (ORDER kernel): the firmware
crashes during the cold boot and no namespace appears. The branch-2
INIT send does not rescue the cold boot. One caveat, recorded for
accuracy: Linux's INIT is sent from the boot path while HELLO handling
runs on a workqueue, so this run cannot prove the INIT reached the
firmware before HELLO arrived, the way m1n1's synchronous sequence
guarantees. The warm E4 run — where INIT necessarily precedes HELLO
because INIT is what wakes the IOP — already failed identically, so
INIT ordering is not supported as the cause on either path.

Two further observations:

- **Same-session m1n1 history does not save the cold boot.** The
  m1n1 cycle minutes earlier in this same power session completed
  cleanly (init, reads, shutdown, payload intact), giving Linux's
  branch 2 exactly the post-m1n1 state the provenance hypothesis
  pointed at. It crashed the same way. For the cold path, session
  history is eliminated alongside construction.
- **A concrete reset difference remains for the cold path.** The
  device tree gives the NVMe node a single reset, `resets = <&ps_ans>`;
  m1n1's proven cycle resets **two** PMGR devices, ANS and ANS2. If
  the `ps_ans` reset does not cover the ANS2 domain, Linux's cold
  boot runs against a coprocessor complex that was never fully reset.
  Whether `ps_ans` covers ANS2 internally is not established from
  these sources — it is the next desk check (kernel pmgr reset ops
  against the ADT PMGR device table). Note this can at most explain
  the cold boot crash; the warm sleep crash involves no reset in
  either construction and remains separately unexplained, with the
  E5 live-session handoff as its remaining test.
