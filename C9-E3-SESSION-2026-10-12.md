# E3 — sleep at probe, before queue creation — Oct 12, 2026

Executes experiment E3 from the
[session-state design](C9-STATE-DESIGN-2026-10-12.md), following
[E1](C9-E1-SESSION-2026-10-12.md). A TRACE-derived kernel adds an
`E3PROBE` hook in the ANS boot path: immediately after BOOT_STATUS OK
(RTKit boot/wake complete, AP ON), before any NVMMU or queue setup, it
runs `apple_rtkit_shutdown_prepare`, stops the CPU, freezes the
management trace ring (phase `e3probe`), and aborts probe either way.
The init's ProbeTest mode paints the outcome; no namespace is expected
and no unbind occurs.

## Interpretation

Pre-registered reading: an ACK here would have implicated queue
creation or a later probe step; no ACK moves the comparison to the
boot itself. **The failure is identical at the earliest possible
moment**: the sleep request crashes the firmware in a session that
has done nothing but boot. Combined with E1 (zero reads) and the
receive-ring run (full session), everything after the boot handshake
is eliminated, and the design table already proved every handshake
message identical to m1n1's working session.

What remains is what a message trace cannot show about how the
session was created. Every failing sleep request was made against a
session **booted by Linux** (warm wake here and in E1/TRACE; reset+boot
in the cold L1 cell); every successful one against a session booted by
m1n1. The next step is desk work, not another run: a register-level
audit of the two boot paths — SART programming, mailbox control
registers and endpoint buffer addresses/sizes, IOP memory carveout,
PMGR/clock state around boot — Linux `apple_rtkit_boot`/`apple_rtkit_wake`
against m1n1's bring-up, looking for the divergence the protocol
comparison cannot see.
