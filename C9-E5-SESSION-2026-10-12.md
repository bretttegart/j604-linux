## Question and construction

Does a successfully restarted m1n1 ANS, kept running into Linux, rescue
the warm Linux sleep failure? This is the live-handoff E5 proposed in
the E4/reset-coverage notes; it supersedes the older cold-direction E5
placeholder in the state-design note.

The disposable C9 local loader gains a one-shot proxy operation:
delete SQ/CQ, shut down and disable the controller, then call
`rtkit_quiesce`. Both AP and IOP become QUIESCED (`0x10`), with the
ASC CPU still running and BOOT_STATUS OK. The operation checks its
Boolean result directly. It does not call sleep, stop the CPU, reset
PMGR, free allocations or remove SART mappings.

Once armed, the final `nvme_shutdown()` retains the live state and
checks CPU RUN / BOOT_STATUS again before Linux handoff. FDT preparation
reserves the current three RTKit buffers and six queue allocations,
rounding each queue allocation to 16 KiB. The host independently checks
that all nine ranges are covered in the **final** FDT and do not overlap
the payload. The old FDT is saved separately; kernel/initramfs are
byte-identical across the storage cycle. The final FDT intentionally differs.

Before retention, the runner performs the proven m1n1 sequence:
init → five checked reads → normal shutdown → second init → the same
five checked reads. Thus the retained session includes a successful
m1n1 cold restart in this power session. Linux then follows its ordinary
warm INIT/HELLO/endpoint negotiation and the E1 immediate-unbind test.
No Linux block reads precede the unbind. No disk write commands, ESP
staging, boot-object replacement or firmware changes occur.

## Interpretation and limit

This live m1n1 handoff does **not** rescue Linux sleep. The failure follows
a verified m1n1 restart, intact payloads, retained mappings and reserved
allocations. Merely preserving the m1n1 RUN/BOOT_STATUS state and its
buffers is insufficient.

Linux sends INIT and renegotiates endpoints. This experiment transfers
hardware/memory state, not the original unchanged RTKit session; it cannot
eliminate state overwritten by that negotiation or by intervening kernel
boot/power management. Quiescing before takeover is another explicit
part of the construction. The result does not prove every possible
live-session adoption would fail, or identify a faulty register.

X1's mailbox evidence strongly associates the crash with SLEEP, and E5
repeats the warm crash signature. However, no advertised ADT register
range at `0x49f0xxxx` does not establish a missing firmware page mapping,
and SError context does not identify the original accessing instruction.
The existing ADT audit and Crg8 analysis already record these limits.
The previous claim that Linux is clean from every angle is too broad:
the measured request/ACK/receive behavior is supported; firmware-visible
state programmed by Linux remains the subject of the investigation.

Next useful experiment: capture the same narrowly selected PMGR/clock,
ASC/mailbox and SART state at the successful m1n1 pre-sleep point and the
earliest failing Linux pre-sleep point (E3), then change one demonstrated
divergence. E5 is not a reason to repeat delay sweeps or restore firmware.
