# J604 live-session adoption — implementation note, 2026-10-28

Draft branch only (`adoption-ram`). No push, no hardware boot, no LabOS
changes. Spec: the adoption handoff contract dated 2026-10-28 (Muse VM,
`goals/m4-pro-linux-boot-watch/files/adoption-handoff-contract-2026-10-28.md`).

## Design in one paragraph

The producer (m1n1, Option A) proves ANS with matching reads, deletes the
admin/IO queues, disables the controller, and hands Linux a *running*
RTKit session — no quiesce, no sleep, no PMGR reset, no buffer/SART free.
The consumer (Linux) adopts that session without sending any management
message, then creates fresh NVMe queues and lets the normal namespace scan
and the existing C9 initramfs read-hash verifier do the first I/O.
Adoption proof is a set of kernel log lines (`ADOPT-*`) plus the producer
diagnostic trace; if any proof line is missing, the run is uninterpretable,
not a pass or a fail.

## How this differs from E5 (the negative control)

| Step | E5 (2026-10-12) | Adoption (this branch) |
|---|---|---|
| Producer power step | `rtkit_quiesce` — AP and IOP to QUIESCED `0x10` | None. CPU must be RUNNING with IOP and AP power ON |
| Producer queues | Delete SQ/CQ, controller shutdown + disable | Same (Option A) |
| Producer shutdown path | Early return in `nvme_shutdown`, retaining state | Same shape, different armed condition (adopt, not live) |
| Linux session step | Warm INIT + HELLO/EPMAP renegotiation via `apple_rtkit_wake` | No INIT, no HELLO/EPMAP, no STARTEP for inherited endpoints, no SLEEP, no PMGR reset before first I/O |
| Linux power step | Full boot handshake, including AP power ON via the handshake | `apple_rtkit_adopt_running`: internal bookkeeping only, zero messages sent |
| Result claimed | "Live handoff does not rescue Linux sleep" — but the session was renegotiated, so adoption was never tested | No claim yet: untested on hardware |

The E5 producer patch (`diagnostics/m1n1-c9/local-to-live.patch`) is the
template for the adoption producer patch, with the quiesce call removed
and the armed condition renamed. That is deliberate: the diff between the
two patches is the experiment.

## Producer (`scripts/prepare-adoption.py`)

Runs on a disposable C9-PREP-* copy that already carries the C9
instrumentation (same precondition as `prepare-c9-live.py`). It edits:

- `src/nvme.h` — declare `nvme_adopt_handoff()` / `nvme_adopt_armed()`.
- `src/nvme.c` — `nvme_adopt_handoff()`: one-shot; requires
  `nvme_initialized`, `nvme_asc`, `nvme_rtkit`; deletes SQ 1 and CQ 1,
  shuts down and disables the controller (reusing the C9 `c9_delete`,
  `c9_ctrl_shutdown`, `c9_ctrl_disable` helpers); then requires, without
  sending anything: ASC CPU running, IOP power ON, AP power ON (via a new
  `rtkit_is_power_on()` accessor — the power fields live in `rtkit.c`'s
  private struct, so nvme.c cannot read them directly), BOOT_STATUS OK,
  CC.EN clear, CSTS.RDY clear. On success it snapshots (phase 31) and
  emits `C9_ADOPT_ARM`. `nvme_shutdown()` early-returns when adopt-armed,
  printing `ADOPT: retain running ANS, buffers and SART mappings`, and
  performs no sleep, stop, reset, or free.
- `src/rtkit.c` / `src/rtkit.h` — `rtkit_is_power_on()`: true only when
  `iop_power == RTKIT_POWER_ON && ap_power == RTKIT_POWER_ON`. This is
  what distinguishes RUNNING from E5's QUIESCED (`0x10`); a quiesced
  session refuses adoption instead of silently accepting it.
- `src/proxy.c` — new one-shot proxy op `0xf06` (E5 used `0xf05`):
  `nvme_adopt_handoff()`. No disk operations.
- `src/c9diag.h` / `src/c9diag.c` — new events `C9_ADOPT_ARM = 25`,
  `C9_ADOPT_RESERVE` (26); `c9_diag_reserve_adopt()` mirrors
  `c9_diag_reserve_live()` (reserve the 3 MAP + 6 QUEUE allocations from
  the last INIT_BEGIN, 16 KiB-rounded, via `fdt_add_mem_rsv`) and
  additionally publishes `/chosen` properties (see below); plus
  `c9_diag_protected_mask()` returning the latest snapshot's SART mask.
- `src/kboot.c` — call `c9_diag_reserve_adopt()` before `fdt_pack()`,
  bailing if it fails (same pattern as E5's reserve call).

Published `/chosen` properties (producer side; consumer reads them):

- `j604,ans-live` (u32, 1) — a live session is offered. The name is
  contract-internal for J604; it deliberately does NOT reuse the Pro's
  `m4,ans-live` name, because that name carries Pro loader semantics.
- `j604,ans-live-controller-state` (string, "disabled") — Option A.
  The consumer refuses adoption for any other value.
- `j604,ans-live-boot-status` (u32) — BOOT_STATUS read at arm time.
- `j604,ans-live-sart-mask` (u32) — latest snapshot SART protected mask.

## Consumer (`patches/linux-adoption-2026-10-28.diff`)

Applies on top of the existing October C9 kernel tree (base 77cb8f2 plus
the uncommitted C9 diffs already in `~/linux-asahi`), not on pristine
upstream. The diff:

- `drivers/soc/apple/rtkit.c` + `include/linux/soc/apple/rtkit.h` —
  `apple_rtkit_adopt_running()`: returns `-EINVAL` if crashed; otherwise
  sets `iop_power_state`/`ap_power_state` to ON as internal bookkeeping
  ONLY (labelled as such in the code — Linux did not observe these ACKs,
  the producer negotiated them), completes the epmap/iop/ap wait objects
  so no path blocks on a negotiation that already happened, and logs
  `RTKit: adopting already-running session (no INIT/HELLO/EPMAP sent)`.
  It sends zero management messages. This is the only new RTKit entry
  point; `apple_rtkit_wake`, `apple_rtkit_boot`, `apple_rtkit_shutdown`,
  and `apple_rtkit_reinit` are untouched.
- `drivers/nvme/host/apple.c` —
  - `struct apple_nvme` gains `bool adopted` and `bool adoption_refused`.
  - Probe reads `/chosen`: if `j604,ans-live` is present and
    `j604,ans-live-controller-state` is "disabled", the controller is an
    adoption candidate; any other state value refuses adoption and the
    probe fails with `-ENODEV` rather than silently falling back to
    renegotiation (a silent fallback would make the run uninterpretable).
    Pre-existing probe snapshot (`NVME-SNAP`) is retained as the
    pre-handoff record.
  - `apple_nvme_reset_work()`: a new branch, checked before the existing
    `apple_rtkit_wake()` branch, for `needs_ioq_register` hardware with
    CPU RUNNING, BOOT_STATUS OK, and an adoption candidate: it calls
    `apple_rtkit_adopt_running()` and logs `ADOPT-PRE` (cpu, boot status,
    SART mask, CC, CSTS) and, after adoption, `ADOPT-OK`. The existing
    wake/boot branches are unchanged for non-adoption controllers.
  - `apple_nvme_reset_work()` head: if `anv->adopted` is already set, the
    RTKit-shutdown block (quiesce + sleep) is skipped — an adopted
    session must not be shut down by a later reset, or the adoption
    result is destroyed by the driver's own cleanup.
  - `apple_nvme_shutdown()` / `apple_nvme_suspend()`: if adopted, skip
    `apple_rtkit_shutdown()` and the CPU_CONTROL clear, logging
    `ADOPT-SKIP-SHUTDOWN`. Rationale: Linux did not start this session
    and must not stop it as if it had; the shutdown path for an adopted
    session is an open question (§"Open questions"), deferred, not
    improvised here.
  - NVMMU/queue setup is UNCHANGED: TCB bases still go to the NVMe
    window as in the October C9 tree (`separate_nvmmu_region = false`,
    comment "raw27: TCB offsets go to the NVMe window, as on t8103").
    The T8132 NVMMU/linear-doorbell placement question is NOT resolved
    by this patch and must not be read as resolved.
  - BROKEN_FUA: not touched. The write phase is separate; this payload
    is read-only by construction (the initramfs never writes).

## Payload and run cell

- Kernel: `Image.gz` + `t8132-j604-ramoops.dtb` from the patched tree.
- Initramfs: rebuilt unchanged from `scripts/build-c9-init.py`
  (C9 Go verifier). No init change was needed: booting with
  `j604.test=ADOPT` selects the `testStorage` path (not a C9 R/E1/E3/E5
  runtime cell), which waits for `/dev/nvme0n1`, requires 4096-byte
  blocks, reads LBAs 0, 1, 2, 128, 4096, and compares SHA-256 against the
  established hashes. It performs no unbind and no sleep — both would
  violate the adoption run.
- Delivery: proxy `linux.py` RAM boot only. No LabOS enrollment, no
  installed image, no NVMe writes.

## Ported from Pro / Aurora vs written for T8132

- Ported (design only): Pro live-session lifecycle — producer proves the
  session, hands it back still running, consumer adopts without
  re-negotiating; Pro loader discipline (bounded polls, read-only
  commands, defined emergency path). No Pro code was copied; the m1n1
  patch is written against upstream m1n1 + the C9 instrumentation.
- Ported (notes only): Aurora T8132 `cold_reset` (PMGR reset only for a
  stopped CPU — excluded at adoption handoff by invariant H1, so no
  reset code is added here) and `needs_ioq_registers` (paired 32-bit
  lo-hi access — already handled by the October C9 tree's IOQ register
  writes, reused unchanged).
- Written for T8132: the J604 DT property names, the Option A
  controller-disabled contract, the RUNNING-vs-QUIESCED power check,
  the adoption-refusal behaviour, and all proof logging. T8132 values
  used: NVMe regs from the J604 DTB (`nvme@4c5cc0000`, reg-names nvme /
  ans / nvmmu), power-domains ans + apcie_sys_st (verified in the live
  DTB), mailbox IRQ order 1003/1004/1005/1006 (verified Oct 7, to be
  re-grepped at run time), BOOT_STATUS OK `0xde71ce55`.

## Open questions (unchanged from the contract, not solved here)

- Exact T8132 NVMMU / linear-doorbell placement. The patch reuses the
  October C9 mapping (TCB to NVMe window). If adopted reads fail, this
  is the first suspect after the adoption proof itself — but changing
  it is a separate experiment, not a tweak to this build.
- Syslog/crashlog buffer ownership across handoff. The consumer keeps
  the existing rx handlers: it answers firmware buffer requests as they
  arrive. If firmware re-requests a buffer the producer already served,
  Linux will allocate a second buffer; the proof log will show the
  re-request, and the run must be flagged. This is labelled, not fixed.
- Whether AP power ON is needed for the firmware to accept NVMe commands
  after adoption. This build deliberately sends no AP power message.
  If adopted reads fail with a live, adopted, but unresponsive session,
  the labelled follow-up variant is "adopt + AP-ON only" — it must not
  be smuggled into this build.
- Shutdown path for an adopted session (see consumer note above).
- DMA ownership on abort, and whether an ANS2 device exists on J604.

## Guesses — labelled explicitly

- G1: The producer's post-init power states are IOP ON + AP ON. This is
  inferred from m1n1's `rtkit_boot` flow (waits for IOP ON, then sends
  AP ON) and from E5's trace (AP/IOP ACKs observed), not from a fresh
  m1n1-side power-state dump. If the arm check fails on hardware, G1 is
  the first thing to verify — the fix is to dump the states, not to
  weaken the check.
- G2: The consumer's namespace scan + initramfs read-hash check is an
  adequate first-I/O proof. It proves identify + reads through adopted
  queues; it does not prove sustained operation, CQ wraps, or writes
  (those are later gates).
- G3: `j604,ans-live` DT properties survive the m1n1→Linux FDT handoff
  unchanged. `fdt_setprop` on `/chosen` in the reserve step is the
  standard path used for initrd properties in the same file; survival
  is verified by the consumer's probe log on the hardware run, not
  assumed here.
- G4: Completing the epmap/iop/ap wait objects in `adopt_running` is
  safe. Rationale: no in-tree caller waits on them after probe except
  `apple_rtkit_boot`, which the adoption branch bypasses; a later
  firmware EPMAP (not expected for an adopted session) would re-complete
  harmlessly. If a crash-recovery path is later found to depend on
  these completions being pending, this must be revisited.
