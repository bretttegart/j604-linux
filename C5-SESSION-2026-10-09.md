## Exact scope

Only `drivers/soc/apple/rtkit-crashlog.c` differs from C4. The source delta
is [linux-c4-to-c5-crashlog-diag.diff](patches/linux-c4-to-c5-crashlog-diag.diff).
It reads only the normal-memory shadow buffer:

- Ccst: print task ID, auxiliary word, and bounded stack addresses.
- CasC: print the six u64 fields named by m1n1's existing decoder. Do not
  assume the register bit meanings from these labels.
- Crtk: validate each 72-byte record and pointer count before advancing;
  print bounded task names, IDs, flags, pointer, and stack count. Keep any
  unparsed-length warning. Record count is capped at 64.
- Cver: print bounded UUID/version metadata and up to 64 raw payload bytes.
- CLHE: print main header fields/bytes; at a rejected section, print its
  fourcc and up to 32 validated remaining bytes. Keep the existing parser
  termination behavior so the suspected footer is measured before a fix.

All C4 unknown-section raw dumps remain. This is not a reset, SART,
mailbox, power-state, firmware, or NVMe behavior change. Kernel config,
`apple.c`, and `rtkit.c` are byte-identical to C4. Stage1 uses the same audit
m1n1 prefix; stage2 uses the same original snapshot m1n1 prefix. DTB and
common initramfs are unchanged. The bootargs label becomes
`j604.test=CRASHLOG-DIAG-A5`.

### First verified findings

PAGE 40/79 maps Crtk **task 12 to `Cmd`**, flags `0000`, six frames.
This is an ID match, not an inference from the printed-name order.
Source: `C5-CAMERA-20261009/sharp-review/segment-014/frame-001.png`.
**This is the C4 task-ID mapping, not C5's crashed task.** C5 Ccst reports
task 14, which the same task table names `power`. See the final findings
below; the preliminary Cmd focus was superseded by that cross-check.

At offset `0x4bc0`, the 32 rejected bytes are:

```text
45 48 4c 43 03 03 00 00 c0 4b 00 00 0a 00 00 00
00 00 00 00 00 00 00 00 00 00 00 00 00 00 00 00
```

They identify `CLHE`, version `0x303` (771), size word `0x4bc0`,
flags `0x0a`, followed by 16 zero bytes. The parser reads +12 as a normal
section length before switching on fourcc. For this footer, +12 is flags;
the resulting malformed-size/no-footer diagnostics are therefore a parser
format problem. The firmware crash precedes parsing, so correcting footer
recognition will not repair ANS startup. Source: `footer-detail.png` from
the initial console recording, with a manually transcribed binary in the
run directory. PAGE 79/79 confirms the same bytes in
`sharp-review/sharp-009/frame-002.png`.

A separate parser correction should recognize a fully bounded CLHE footer
before normal section-length validation, preserve main-header/ordinary
section bounds, and be checked offline with this footer and truncated
variants. Do not spend a new hardware boot solely to reconfirm this format.
