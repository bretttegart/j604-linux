# J604 bring-up review — 2026-10-07

> This is the original static review. Muse has since executed the A/B tests:
> tethered A passes and both chain variants fail. See the
> [results follow-up](FOLLOWUP-2026-10-07.md) and the
> [post-audit plan](POST-SHUT-AUDIT-PLAN-2026-10-07.md) for updated
> conclusions and the next experiment. The roadmap below remains applicable.

The immediate problem is the ANS storage coprocessor transition between an
m1n1 SSD session and Linux. The recorded tethered path already reaches Linux
userspace and reads the internal SSD. Recover that as the control, repair the
diagnostics, and compare the RTKit startup sequences before changing more
NVMe register settings. A first graphical desktop can be developed through
the tethered path while untethered storage handoff is investigated.

For execution, use [the Muse runbook](MUSE-RUNBOOK.md) and append outcomes to
[the test ledger](TEST-RESULTS.md). This document is the supporting audit;
the runbook specifies the first controlled comparison.

This is a static review of repository commit `1719e0b`, the local source
trees, payload contents, logs, and selected recorded frames. No new Mac boot
or disk write was performed. Historical successes below are recorded test
results, not newly reproduced results. The precise firmware assertion behind
the latest crash remains undetermined.

## What is already established

- The project records 10/10 CPUs, SMC, built-in keyboard input to a VT, and
  initramfs userspace working. CTRR_C/CTRR_D reservations were central to SMP.
- Raw34 fixed the tethered NVMe handshake by calling `apple_rtkit_wake()`.
  Raw35–36 recorded GPT/block-read success. The test checks `EFI PART` at
  byte 4096, consistent with the reported 4Kn namespace. This is a useful
  smoke test, not yet broad storage validation.
- The repository records stage1 loading stage2 from the FAT ESP and reaching
  Linux. The failure is reported after Linux starts ANS from a stopped state:
  `CPU_CONTROL=0`, `BOOT_STATUS=0`, branch 2, a coprocessor crash, then `-62`.
  The timeout alone does not identify the firmware's original fault.
- The latest host transcript, `~/j604-boot/chainload-raw52.log`, actually
  uploads `stage1-diag.bin`. Its payload variable loads `/stage2-diag.bin`
  from an ESP. A host reconnection timeout is not sufficient evidence of a
  failed boot: an automatically booting stage2 need not return to the proxy.

## Findings that change the interpretation of previous tests

### 1. The recorded “reboot handoff” experiment misses the successful path

In `~/m1n1-ctrr/src/chainload.c:117`, the normal chain is:

```text
nvme_init -> rust_load_image -> nvme_shutdown -> chainload_image
```

The added `rtkit_boot()` in
[`patches/m1n1-nvme-reboot-handoff.diff`](patches/m1n1-nvme-reboot-handoff.diff)
is at `nvme_init()`'s `out_shutdown` error-cleanup label
(`~/m1n1-ctrr/src/nvme.c:450`). It is not in the successful
`nvme_shutdown()` path at line 540. That path still sleeps ANS, resets it,
and frees its buffers.

Consequently, raw47 does not establish that a correctly implemented
restart-before-handoff strategy was tested and refuted. The current
`stage1-diag.bin` and `stage2-diag.bin` bootloader prefixes match the current
local m1n1 build, which contains this source arrangement. Historical deployed
artifacts would still need their own hashes before making a stronger claim.

Simply moving the call is insufficient: the error path immediately follows
the restart with `rtkit_free()` and `sart_free()`. Those release shared
buffers and remove mappings while the restarted IOP may still use them.
A running-IOP handoff needs an explicit lifetime/ownership contract for
firmware buffers, queues, SART entries, and reserved RAM. A stopped, cleanly
rebootable IOP is the simpler initial target.

### 2. A startup protocol difference deserves a controlled experiment

The two similarly named boot functions do different things:

| Implementation | Sequence |
|---|---|
| m1n1 `rtkit_boot()` (`src/rtkit.c:496`) | Start CPU; send IOP `INIT` (`0x220`); negotiate HELLO/endpoints; await IOP ON; send AP ON. |
| Linux cold branch (`drivers/nvme/host/apple.c:1107`) | Assert reset; reinitialize host RTKit state; deassert reset; set CPU RUN; call `apple_rtkit_boot()`. |
| Linux `apple_rtkit_boot()` (`drivers/soc/apple/rtkit.c:852`) | Wait for endpoint map and IOP power ACK; send AP ON. It does not send IOP INIT. |
| Linux `apple_rtkit_wake()` (`drivers/soc/apple/rtkit.c:955`) | Send IOP INIT, then call `apple_rtkit_boot()`. |

Hypothesis: the post-m1n1 ANS state requires explicit INIT even after CPU
restart. This is supported by the successful tethered wake change and the
m1n1 sequence, but is not proven. Firmware can behave differently after
reset, and an unsolicited HELLO or power ACK could create ordering races.

After obtaining a complete baseline trace, test only the T8132 cold branch
with `apple_rtkit_wake()` after CPU RUN in place of `apple_rtkit_boot()`.
Leave the reset sequence, DTB, queue programming, EP7 implementation, and
bootloader fixed. Record message order and the actual state reached, even
if the final result is still a crash. This is an experiment, not a proposed
unconditional change for every Apple SoC.

### 3. The diagnostic payload discards important evidence

- `ANSBR 3` is inside a block comment in
  `~/linux-asahi/drivers/nvme/host/apple.c:1142`. Its string is absent from the
  embedded kernel, while `ANSBR 2` is present. A displayed `BR0` therefore
  cannot exclude the warm branch.
- [`init/init.go`](init/init.go) `diagLines()` truncates each matching line
  to 76 bytes and keeps only the last 45 lines. Long mailbox histories can
  push the original assertion, firmware version, or branch snapshot out.
- The classifier searches for `RTKit crashed`; the actual core message is
  `RTKit: co-processor has crashed`. Preserve coprocessor/device identity
  because RTKit is shared by several devices.
- `drainKmsg()` reopens `/dev/kmsg` on each call, so the two snapshots can
  repeat existing messages. Use sequence numbers or one continuously read
  descriptor. Distinguish current logs from previous pstore logs.
- The kernel has a 128 KiB printk ring (`CONFIG_LOG_BUF_SHIFT=17`) and
  `CONFIG_DYNAMIC_DEBUG` is disabled. `loglevel=8` alone cannot enable
  compiled-out `dev_dbg()` protocol messages.

Use a larger log ring and explicit RTKit handshake logging. Save the full
current dmesg in RAM, retain the binary crash buffer before the crash callback
returns, and expose it through a supported retrieval path. The current
RTKit crash handler frees its shadow copy after the callback; any retained
copy must own its memory. If the framebuffer is the only working channel,
page the complete log with page/boot identifiers and repeatable navigation
or timed cycling. The already working keyboard is useful here. Capture the
first assertion, not only the tail of the dump.

The existing parser handles `Cstr`, `Cver`, `Cmbx`, `Ctim`, and `Crg8`.
Preserve unknown sections and inspect their actual FourCCs and lengths before
assuming that `Csta`/`Cnvr` contains the answer. A screenshot is not enough to
reconstruct the complete binary crash buffer reliably.

### 4. Check shutdown success instead of assuming it

`~/m1n1-ctrr/src/rtkit.c:717` has a return-type mismatch: `rtkit_sleep()`
stores the Boolean result of `rtkit_switch_power_state()` in an integer,
tests `ret < 0`, then stops the CPU and returns zero. The underlying Boolean
failure can never satisfy that comparison. NVMe callers also ignore the
return value. This is a concrete error-propagation defect, not proof of the
current crash's cause.

Normalize the return convention and log/check quiesce, sleep ACK, controller
disable, and reset results before trying new warm handoffs. Instrument both
normal shutdown and initialization failure cleanup with different markers.
Do not count a firmware shutdown as clean merely because CPU RUN became zero.

### 5. Firmware and on-disk artifact provenance remain inconsistent

The README at reviewed commit `1719e0b` says the October 5 DFU restore
eliminated firmware 27.0. However,
the October 7 raw52 log reports OS mBoot `18000.161.10.701.1` and system mBoot
`20457.1.29`, mapped to 26.7 and 27.0 by this m1n1 tree. Raw34's successful
boot also reports these identifiers. Thus the existing records do not
support firmware mismatch as a sufficient explanation of the regression,
or support the claim that it has been eliminated.

Record the raw ADT firmware identifiers, installed OS build, and booted
LabOS identity together on the next run. Resolve the discrepancy before
considering any firmware change. A downgrade/restore is not the next test.

Also compare the ESP's actual stage2 hash with the host artifact: rebuilding
`~/j604-boot/r5/stage2-diag.bin` alone does not update the file stage1 reads.

## Ordered next experiments

1. **Repair evidence collection and freeze a manifest.** Record source
   commits/diffs, configuration, payload hashes, boot path, firmware IDs,
   current-boot marker, and expected branch. Keep a known working payload.
2. **Reproduce the direct tethered control.** Fresh boot into the installed
   proxy, load the saved CTRR bootloader, then use `linux.py` with the same
   kernel/DTB/initramfs under investigation. The diagnostic changes should
   be shared between the control and failing run. Verify namespace geometry
   and repeated read-only checksums, including GPT reads.
3. **Reproduce the SSD-chain case with identical Linux inputs.** Verify the
   loaded stage2 identity. Capture ANS state before and after stage1 shutdown,
   Linux reset, HELLO, endpoint map, each buffer reply, IOP power ACK, AP ON,
   and the first crash. Record SART entries' address/size/flags in addition
   to an occupied-slot mask. A free-slot count alone does not prove correct
   DMA permissions. Take these snapshots in the owning driver, not arbitrary
   live proxy MMIO reads.
4. **Run the T8132 cold INIT experiment described above.** Success means
   handshake completion, controller readiness, namespace enumeration, and
   repeatable reads across fresh boots. A different failure is still evidence
   if the trace identifies where the sequences diverge.
5. **If needed, isolate the predecessor state.** Compare an m1n1 NVMe
   init/read/clean-shutdown cycle followed by the same Linux payload with the
   full FAT/second-stage chain. Separately boot a DTB with NVMe and any newly
   unused supporting nodes disabled to check whether the rest of the chain
   reaches a stable shell. Preserve the shared ANS power domain. These tests
   separate storage restart, second-stage memory layout, and unrelated boot
   failures. Make one change per run.
6. **Only then revisit reset, SART, and warm adoption.** Use the binary crash
   and protocol divergence to choose the next change. A warm strategy must
   prove CPU RUN/state, keep all firmware-visible memory valid across stage2
   relocation and Linux allocation, and document who replaces each mapping.

Do not repeat the old queue-size, IRQ-swap, and NVMMU-window permutations
without new evidence pointing there. Their historical results are valuable,
but the experiments did not eliminate every possible interaction forever.
Pstore returning no records means the current recovery path was unproductive;
it does not prove that persistent logging can never work. Prioritize current
RAM logs over another reboot-dependent logging investigation.

## Roadmap to a graphical desktop

| Milestone | Work | Acceptance criterion |
|---|---|---|
| Reproducible development boot | Freeze the tethered control; make logs complete; replace the paint-only init with an interactive recovery shell. | Repeated boots, working keyboard, readable current logs, stable idle, repeated read checksums. |
| General Linux userspace | Make a desktop-capable kernel configuration and a lean ARM64 userspace, initially loaded through the working tethered route or RAM. | Shell, device discovery, filesystems, services, and input work without the diagnostic init. |
| First visible GUI | Test the existing boot framebuffer through simpledrm, CPU rendering, and a minimal compositor/window manager; enable evdev and validate pointer input. | A local window, keyboard input, and a usable pointer. Fixed display mode and slow rendering are acceptable at this milestone. |
| Persistent Linux root | Validate sustained reads, then writes confined to the intended dedicated Linux partition; install the chosen ARM64 root filesystem. | Verified writes/checksums/fsck and repeated tethered boots into the persistent root. This can precede an untethered fix. |
| Untethered desktop | Complete ANS restart and stage handoff; provide a selectable known working boot image. Introduce U-Boot/EFI only when its M4 path is validated or needed by packaging. | The same root and desktop boot from LabOS without a host payload transfer. |
| Accelerated desktop | Integrate a pinned, compatible Gravity bootloader/kernel/firmware/Mesa set; bring up J604 AGX/DART/power data and the internal display path. | GPU test jobs and GL rendering pass; the desktop uses the hardware renderer; modesetting and repeated starts work. |
| Useful laptop | Network, touchpad completeness, brightness, battery/charging/thermal reporting, power management, then audio, camera, external outputs, suspend/resume. | Measured stability, temperatures, battery use, and recovery across normal laptop use. |

The existing kernel is intentionally tiny. It already enables simpledrm,
but disables `CONFIG_INPUT_EVDEV`, `CONFIG_NET`, `CONFIG_CGROUPS`,
`CONFIG_TMPFS`, `CONFIG_EXT4_FS`, `CONFIG_BTRFS_FS`, and `CONFIG_VFAT_FS`.
A full rootfs or desktop cannot be dropped onto this exact configuration
and expected to work. Enable the needed facilities and account for a larger
image using the tethered loader or a validated disk-loading path.

Keyboard-to-VT success does not establish touchpad or userspace evdev support.
Likewise, boot framebuffer output is separate from full DCP/internal-panel
modesetting, and GPU rendering is separate from either display path. A
software-rendered GUI can test userspace before either full GPU or panel
support is complete; it is a feasibility milestone rather than a comfortable
daily desktop at the panel's native resolution.

Gravity currently lists the base-M4 MacBook Pro as WIP, while its M4 mini
alpha ships a graphical stack. That makes its stack a strong integration
base, but does not establish J604 support. See the
[current support list](https://gravitylinux.org/) and
[alpha release notes](https://gravitylinux.org/blog/early-alpha-m4-mac-mini/).
Asahi's [M4 matrix](https://asahilinux.org/docs/platform/feature-support/m4/)
tracks its own support and should not be treated as a matrix of Gravity's
downstream capabilities.

The [GPU article supplied during this review](https://codyho.dev/blog/gpu-driver/)
describes both a kernel firmware driver and a Mesa implementation. Reusing
that pair makes more sense than starting a J604 GPU driver from zero. Because
J604 and the supported base-M4 mini share T8132, substantial reuse is a
reasonable inference; board resources, firmware ABI, and the laptop display
still need validation. Pin compatible components rather than assuming an
arbitrary existing Asahi Mesa package implements the new GPU support.

The quoted procedure involving a 27.0 IPSW, kernelcache, Exclave support,
and a macOS desktop concerns getting macOS running under the research
hypervisor. It is a separate development track from directly booting this
Linux payload. In particular, downloading an IPSW for a guest experiment is
not a reason to restore or upgrade the Mac's firmware. The SPTM PR discussion
also distinguishes the intended 26.6 firmware family for M4/A18 Pro from a
later 27.x target for M5.

If reverse engineering becomes necessary, first obtain a minimal trace of
the specific ANS reset/initialization or J604 display transaction. Making a
full macOS desktop work, or implementing M5-specific guest features, should
not become a prerequisite for the already working M4 Linux tethered route.
Maintain an isolated hypervisor build if pursuing this research so the
working CTRR/proxy baseline stays reproducible.

No reliable calendar estimate follows from the current evidence. The first
tethered GUI is substantially nearer than an accelerated, power-efficient
laptop with working suspend. Treat those as separate milestones.
