## Unknown-section bytes and limits of interpretation

`PXL_20261009_175351933.jpg` contains all 16 hex rows (256 payload bytes).
Offsets below identify section headers; the payload begins 16 bytes later.

| Section | Header offset | Decoded byte content |
|---|---|---|
| Cnvr, 64 bytes | 0x46e0 | NUL-terminated `storage-prev-assert` at payload offset 0; `0,0,0,0` at offset 48; other bytes zero |
| Cnvr, 64 bytes | 0x4730 | NUL-terminated `storage-prev-assert-stored` at payload offset 0; `0` at offset 48; other bytes zero |
| Csta, 32 bytes | 0x4780, 0x4b30, 0x4b60, 0x4b90 | All four identical: little-endian u32 words `[2, 0, 2, 0, 87, 0, 0, 0]`, equivalently u64 words `[2, 2, 87, 0]` |

These strings are concrete evidence, but they do not supply a current
assertion location, assertion message, or verified field meanings. The
zeros alone do not establish that the firmware has no assertion or that
its persistent state is healthy. The Csta numbers have no identified
schema; do not turn 87 into an errno or select a power-state fix from it.

The same photo reads exactly:

```text
RTKDIAG crashlog malformed section size 0xa at offset 0x4bc0 (crashlog size 0x4be0)
RTKit: End of crashlog reached but no footer present
RTKDIAG crashlog first crash notification, crashlog buffer size=8000
```

The allocated buffer is 0x8000 bytes, larger than the declared 0x4be0.
The final 32 bytes remain uncaptured. The parser reads section length at
header offset +12 and validates it **before** checking for the CLHE footer
fourcc. A CLHE header has a different 32-byte layout, with flags at +12.
Therefore the 0xa rejection could be footer-format handling; this is an
inference, not a confirmed footer or proven firmware corruption. Capture
the final bytes/fourcc before changing the parser's interpretation.
