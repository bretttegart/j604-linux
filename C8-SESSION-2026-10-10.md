### What pages 1–13 + the console tail establish

The ANS rtkit-helper boot sequence on the cold path, kernel-log times
[200]–[234], pager pages 11–13:

- `wake send IOP INIT` — mgmt tx type=6, msg state 0x220 (INIT), ret=0
- rx HELLO (protocol version 12); HELLO reply tx type=2, ret=0
- rx EPMAP (bitmap 0x517); `boot epmap ret=0 boot_result=0`
- mgmt tx type=5 (START_EP) series, ret=0
- crashlog buffer req/reply on ep=1; buffer req/reply on ep=4
  (size=4096, iova assigned)
- `boot wait iop ack` → rx mgmt type=7 →
  **`rx IOP_PWR_ACK msg=0070000000000020 new_state=0x20`**

That ACK is the one whose absence produced the IOP-ACK-wait −62 in
C4–C7. In C8 it ARRIVED. The boot progressed past the entire RTKit
bring-up that used to be the wall.

A reset error −62 still occurred (trace header line:
`reset-error ret=-62 cap=1024`), so something failed at a LATER stage
than the ACK wait. Which reset, and what the firmware did next, is in
pager pages 14–103 — NOT yet captured.

Live trace: seq runs past 98 in the console tail; a `dropped` marker
sits at seq 77 (an unknown number of events were lost mid-stream;
exact count/total not yet cleanly read).

### Caveat — do not over-conclude

Two alternative explanations for the ACK arriving in C8 but not C7 are
both live: (1) run-to-run / firmware-state differences, (2) the C8
trace instrumentation itself perturbing mailbox timing (the known
Heisenbug risk of tracing a timing-sensitive path). The wake phase in
this build also sent IOP INIT as part of its audited wake sequence —
that is distinct from the refuted cold-branch INIT theory, which stays
refuted. No sequencing patch, IOP OFF, INIT experiment, or firmware
intervention is justified by C8 as it stands.

Results — run 2 reproduces run 1's new shape exactly:

- Helper phase fully succeeds: IOP_PWR_ACK rx [234],
  `boot iop ack ret=0` [235], mgmt type=11, ep=2 buffer,
  AP_PWR_ACK [242], `boot AP ON ret=0` [243].
- ANS reset/CPU-run `ANSRST post-cpu-run ret=0` [264]; the firmware
  answers the NVMe driver's own RTKit session: HELLO [266], EPMAP x2,
  START_EP series, crashlog/IOReport buffers — all ret=0 [265-296].
- **The co-processor crashes at kmsg [298], during the NVMe driver's
  `boot wait epmap`** ("RTKit: co-processor has crashed"). The pager's
  own summary names this as FIRST CRASH; CRASH DEVICE nvme-apple.
- Everything -62 is downstream wreckage: the NVMe driver's own
  `boot iop ack ret=-62` [1339], ANSCHK post ret=-62 [1340], and the
  FINAL ERROR `[1441] nvme nvme0: Reset failure status: -62`.
  CPU_CONTROL 0x16, BOOT_STATUS 0. No /dev/nvme0n1.
- Trace: phase=reset-error window only; **total=97, dropped=0**,
  cutoff_ns=1125256588. KMSG 3,189 lines, 0 gap markers.

Interpretation: the wall is no longer "the firmware never ACKs" — with
the traced kernel it ACKs the helper, powers the AP, boots, and serves
a second RTKit session partway, then dies during that session's epmap
wait. The only kernel delta C7->C8 is the trace instrumentation
(config identical, hashes in the manifest), so cold-start timing
sensitivity in the firmware is the leading hypothesis class; firmware
state drift across the day's boots is the alternative. Next
discriminator candidates (not yet run): an untraced kernel with only a
small delay perturbation in the ANS boot path, or epmap-wait tracing
inside the nvme-apple boot sequence itself (C9) to capture the exact
endpoint set outstanding when the crash lands.
