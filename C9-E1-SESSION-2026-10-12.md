## Interpretation

Pre-registered reading: an ACK here would have implicated queue use
after probe; an identical failure puts the poison in probe itself.
**The failure is identical with zero reads** — same ring total (105;
the reads generate no management traffic), same single crashlog
receive in the same millisecond, same `-62`. Session activity after
probe is eliminated. What probe establishes before the request —
the wake/boot handshake, endpoint and buffer setup, queue creation,
controller enable — is the remaining surface, and the wake IOP ACK
state now capture-verified identical (`0x20`) removes the last
unverified handshake value.

Next per the design queue: E3, a diagnostic kernel that runs the
prepare sequence immediately after RTKit boot and AP ON in probe,
before any queue creation. ACK there implicates queue creation or a
later probe step; no ACK moves the comparison to register-level
session state left by the boot handshake itself.
