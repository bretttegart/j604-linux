## Decision after capture

Use the raw bytes to verify the decoded layout before interpretation. Keep
each section's type/index and physical slot order; direction, ring index
semantics, wrap, and timestamp order require evidence from this firmware.
For known management endpoint 0, the existing RTKit code uses message bits
59:52 for type and 15:0 for power state: type 6 is IOP request, type 7 is
IOP ACK, and type 0xb is AP power request/ACK. State 0x20 is ON and 0x220
is INIT. Preserve full words and correlate with Linux's request/ACK logs.

An identified sequencing mismatch can justify a single targeted follow-up.
An exchange that agrees with the expected protocol can shift attention to
firmware-visible state and tethered-path replication. Missing ACKs, finite
history, or unresolved direction alone do not prove either cause; the
capture may remain inconclusive. Do not revive the already-refuted INIT
theory or use IOP OFF. The firmware version split remains a verified
observation and does not justify a reflash.

## C7 findings and next discriminator

The type-0 history retains earlier activity followed by the current boot.
Storage slots 65/66 contain endpoint-0 message `00b0000000000010`
(AP QUIESCED); slot 67 contains `0060000000000001` (IOP SLEEP).
Slots 68/69 then contain HELLO `00100000000c000c` and its reply
`00200000000c000c`. Slots 70–73 contain the endpoint-map exchange,
including final map `0088000100000003` and reply `0088000100000000`.
Linux's own RX/TX diagnostics agree with these full words and report
successful sends. START_EP messages and crashlog/IOReport buffer setup
follow; the tail contains endpoint-4 IOReport traffic. No type-7 IOP ACK
is present in the current cold interval, slots 68–127. **Correction from
the earlier selected transcription:** an older ON ACK is present in slot
35 (`0070000000000020`, timestamp `3714b0a4`), before AP ON in slots 36/40
and the later audited shutdown. The earlier statement that no ACK was
visible anywhere in the section was too broad. This retained history
includes a successful earlier ON exchange but is not a complete trace
of that earlier boot.

The type-4 section contains endpoint `0x21` messages. Five older entries
have timestamp-low values near `0x0505xxxx` and padding zero; two later
entries are `040b000000000000` at `3893c170` / `3893cf49`, padding one;
slot 7 is `0401000000000000` at `59017dbc`, padding one. The current boot's
HELLO/endpoint setup and IOReport traffic have timestamp-low values near
`0x5901xxxx`. That makes the last application record a useful comparison
anchor, but its message meaning and direction are not established here.
Do not decode application endpoint messages using management type bits.

The kernel's actual cold branch (`ANSBR 2`) starts the CPU and calls
`apple_rtkit_boot()`. It waits for EPMAP and the firmware's initial IOP ACK;
it does **not** send INIT or an IOP ON request in this branch. Therefore
absence of such a request in Cmbx is expected and is not a sequencing bug.
The recorded crash notification appears after endpoint/buffer setup;
Linux eventually reports IOP-ACK wait -62 and `crashed=1`. Missing ACK is
consistent with the early crash, without identifying its cause.

**Decision:** C7 demonstrates a fresh RTKit handshake after the audited
sleep/reset path, with no demonstrated management-protocol mismatch.
It does not resolve physical reset/power timing versus firmware-visible
state. There is no supported sequencing patch or reflash from these data.
The next useful discriminator is a bounded comparison of the successful
tethered path's early management/IOReport and endpoint-0x21 traffic against
this captured cold path, with the same image provenance. Establish that
comparison before changing reset ordering or replicating guessed state.
No unchanged repeat, IOP OFF, INIT experiment, or firmware intervention
was performed after capture.
